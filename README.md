# TAI (Team AI)

[![License: Apache 2.0](https://img.shields.io/badge/License-Apache%202.0-blue.svg)](LICENSE)

**Run software delivery — Kickoff, Story, Bug, and Spike work — through a fixed roster of
AI personas, each with their own permissions, human checkpoints, and Confluence outputs,
driven against your real Jira, Confluence, and Bitbucket or GitHub.**

TAI isn't a chatbot wrapper. It's a process: nine named personas (Analyst, PM, Architect,
UX Designer, Developer, DBA, Code Reviewer, Tester, DevOps) each own a slice of the
software-delivery lifecycle, hand off to each other through real Jira tickets, and stop
for a human sign-off at the points that matter (`brief §3.4` — human sign-off is the
default everywhere, not an opt-in safety net). It works against a real Jira/Confluence setup
with Bitbucket or GitHub, or fully locally with no external services at all.

`PROJECT_BRIEF.md` is the single source of truth for TAI's design, decisions, and open
questions — this file only covers getting it installed, configured, and used. If anything
here and the brief ever disagree, the brief wins.

## Why TAI exists

AI coding assistants make one person fast. They also break what teams rely on: shared
state, ownership, review and oversight. The work happens in one person's chat or local
folder, nobody else can see what was decided or why, and "a human reviewed it" often
means "a human clicked approve."

TAI puts AI work inside the system of record your team already uses (Jira for work,
Confluence for designs, Bitbucket or GitHub for code), with a human accountable at every step. A
human architect oversees the AI Architect, a human developer oversees the AI Developer,
and so on, so the whole team can see, review and gate what the AI does.

### What it does about it

- **Work lives where the team can see it.** Every unit of work is a real ticket; designs
  are linked Confluence pages; code and review live in PRs. Every session starts from that
  state, not from someone's chat history, so a different person, or a different AI host
  (Claude Code or Gemini CLI), can pick the work up.
- **Rules are enforced in code, not just written down.** A merge needs a fresh approval,
  finished test tiers and passing checks. Review findings can't be posted until they have
  been rendered for the human. A subtask can't start while a prerequisite is open. Where a
  rule can only be a convention, TAI makes it visible instead: every comment the CLI posts
  is stamped as coming from a session, and sign-offs record whether a session or a person
  made them.
- **An AI never certifies its own work.** The Code Reviewer never edits code, the Tester
  can't mark its own results, and nothing completes without a human. Reviews have to show
  what they read and ran, and verification is against numbered acceptance criteria, with a
  same-session check labelled as not independent.
- **Context stays small and relevant.** The ticket, its parent Story and the pages linked
  to them are what get loaded, typically a small slice of the project, not the whole
  repository or board; everything else is fetched on demand. That only works because the
  links between tickets and pages are kept up.
- **Status, decisions and designs have one home.** There's no second project-status
  document to keep in sync by hand. Because everything is structured and linked, a
  browsable project wiki could be generated by scanning these sources; that is a possible
  future addition and isn't built yet.
- **It runs as you.** No background service, nothing on a timer. A human starts every piece
  of work, and the AI acts with your own permissions and nothing more.
- **The process shrinks when it should.** There's a light lane for a two-sentence change,
  and the full Kickoff is for new initiatives.

### Built on good ideas

TAI borrows ideas from three projects and copies no code. From
[BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD): the roster of role personas,
course correction and retrospectives. From GSD (Get Shit Done): atomic commits tied to units
of work, an independent verifier, fresh-context review and a fast lane for small changes. From
[SpecKit](https://github.com/github/spec-kit): numbered requirements and acceptance criteria,
explicit uncertainty markers and readiness checks. What TAI adds is the thing all three
leave out on purpose: several people, with real accountability, working through the AI
together.

### Built by itself

TAI is developed through TAI. This repository's own work is Jira tickets, reviewed pull
requests and recorded decisions, and most of its rules exist because a session once did the
wrong thing: summarized a list instead of showing it, posted findings nobody had seen, left a
finished Story open, or let an approval go stale. Each became a check.

### Who it's for, and who it isn't

For teams of two or more already on Jira and Confluence, with code on Bitbucket or GitHub, who want AI help without
giving up review, ownership and audit. Everyone on the team benefits from the visibility,
and leads and managers will likely drive the adoption. It isn't for solo speed-running, and
it isn't an autonomous agent that works unattended: parallel and unattended runs are
deliberately out of scope.

### The honest limits

- It adds structure (tickets, criteria, sign-offs). If your team doesn't want that, TAI will
  feel like overhead.
- Some gates are conventions made visible, not enforced. A person can still sign off in the
  wrong place.
- A reviewer that is the same model as the author is still the same model; a fresh context
  helps but isn't independence.
- Work and documents need Jira and Confluence today; code can be on Bitbucket or GitHub. A
  local filesystem backend exists for trying it out and for solo work.
- It has run on itself and on one real project. Expect rough edges.

## How it works

- **A unit of work is a Jira issue** — an Epic decomposes into Stories/Bugs/Spikes/Kickoffs,
  each of which decomposes into subtasks (`Research`, `Dev`, `IntegrationTest`, …). Every
  subtask has exactly one owning persona.
- **Personas hand off through Jira, not through chat.** Asking "what's ready?" or working a
  specific ticket always starts from real Jira/Confluence state — cached locally for
  offline work, refreshed on demand — never from conversation memory alone.
- **Checkpoints are real, not cosmetic.** Some subtasks (e.g. `UAT`, `EpicReview`) are
  *inherently* human-gated — an AI persona can drive the work, but only a human can sign
  off. A human starts every piece of work and signs it off; nothing completes itself.
- **Nothing runs on a timer.** There's no background daemon watching Jira. Every step
  happens because a human (or an AI session acting for them) explicitly asks "what's
  ready?" or "work this ticket" — see [Usage](#usage) below.
- **Two storage backends, one interface.** A `filesystem` backend (the default) needs
  nothing but a local folder — good for trying TAI out or a genuinely solo project. A
  `jira` backend talks to real Jira/Confluence over their REST APIs, authenticated as your
  own account, so an AI persona only ever acts with the permissions you already have.

## Requirements

- **Node.js 24+** (this repo relies on `import.meta.main` and the native `process.loadEnvFile`).
- **[Claude Code](https://claude.com/claude-code) or [Gemini CLI](https://github.com/google-gemini/gemini-cli)** — TAI's commands are slash-command skills for either.
- For the real backend: a **Jira** site (Cloud), a **Confluence** space on the same site,
  and (optionally, for PR-driven work) a **Bitbucket** or **GitHub** repo — each with API-token access.
  The filesystem backend needs none of this.

## Installation

TAI installs itself **once per machine**, at a fixed location (`~/.tai-framework`), and
every project on that machine shares the one install:

```bash
git clone git@github.com:dmayhak/tai-framework.git ~/.tai-framework
cd ~/.tai-framework
npm install
npx tsx src/hosts/cli.ts install-global
```

Clone it directly to `~/.tai-framework` — don't clone elsewhere and move it. `install-global`
writes global skill files for **both** Claude Code and Gemini CLI that point at this exact
clone as TAI's fixed home; it doesn't copy files anywhere.

This is a manual, one-time bootstrap by necessity: the `/tai-*` slash commands (listed under
[Usage](#usage)) don't exist in your AI CLI until `install-global` has written them, so
there's nothing to run *before* this step. Once it's done, those commands exist in every
future session, in every project, on this machine — no re-bootstrap needed, and no
separate install per project.

## Updating TAI

TAI is a normal git clone, so updating it is pulling and re-running the installer:

```bash
cd ~/.tai-framework
git pull
npm install            # only needed when package.json changed
npx tsx src/hosts/cli.ts install-global
```

- `install-global` is safe to re-run. It rewrites every `/tai-*` skill file for both Claude
  Code and Gemini CLI, so new commands appear and changed ones are refreshed.
- **Restart your AI CLI afterwards.** Gemini CLI does not pick up refreshed skill files in a
  running session: quit and restart the process (`/clear` is not enough). If a new or changed
  command doesn't show up in Claude Code, start a new session. An apparent failure right
  after an update is often a stale skill, not a real gap.
- [`CHANGELOG.md`](CHANGELOG.md) lists what changed, newest first, with the reason for each change.
- If TAI is checked out on a branch other than its default (a development checkout), every
  persona turn says so in one line, since the instructions you are following aren't the released ones.
- **Projects you already set up** keep working. The short TAI section in a project's
  `CLAUDE.md` and `GEMINI.md` is replaced in place, never duplicated, and the rest of those
  files is left alone; to refresh it after an update (for example to pick up a new command's
  mention), run `init claude-md` or `init gemini-md` from inside the project (see the
  [setup checklist](docs/target-project-setup-checklist.md)).

## Configuration

### Quickstart: try it locally, no external services

The `filesystem` backend is the default — it needs nothing but a working directory and a
name for yourself. From inside any project you want to try TAI against:

```bash
export TAI_PROJECT_KEY=DEMO
export TAI_HUMAN_ID=you@example.com
export TAI_HUMAN_NAME="Your Name"
export TAI_HUMAN_EMAIL=you@example.com

npx --prefix ~/.tai-framework tsx ~/.tai-framework/src/hosts/cli.ts issue create DEMO story "Try out TAI"
npx --prefix ~/.tai-framework tsx ~/.tai-framework/src/hosts/cli.ts issue search project=DEMO
```

This creates real, locally-persisted issues under `.tai/` in your current directory (gitignore
it) — no Jira account needed. It's the same code path the real backend uses, just backed
by files instead of the Jira REST API, so everything in [Usage](#usage) below works the
same way. This is also the right mode for a genuinely solo project that will never need
Jira at all.

### Real setup: Jira + Confluence + Bitbucket or GitHub

For a real target project, run `/tai-init` from inside that project's own repo. It checks
`init status`, and if the project isn't fully initialized it hands you one command to run in a
**separate terminal** (an assistant's own shell can't prompt you or open your editor, and a
token pasted into chat would go to the model provider):

```bash
cd <your project>
npx --prefix ~/.tai-framework tsx ~/.tai-framework/src/hosts/cli.ts init run
```

`init run` is one idempotent command for both a brand-new project and an **already-onboarded
project you've cloned into a new folder or onto a new PC** (a fresh clone has no `.env` or
`.tai/`, since both are gitignored). It:

1. asks for your **Atlassian site URL**;
2. writes a `.env` skeleton and opens your `$VISUAL`/`$EDITOR` so you fill in the secrets
   (Jira email + API token; for `git-pr`, a Bitbucket email + token, or a GitHub token, with
   repository and pull-request access) — secrets are only ever typed there, never into chat;
3. **discovers** the Jira project, Confluence space and git repo live and lets you pick,
   keeping any `.env` value the live lists confirm; the git host (`TAI_GIT_HOST`) is taken from
   your clone's `origin` remote;
4. **verifies** Jira, Confluence and the git host against the real APIs, stopping at the first
   failure with a concrete to-do list (the git host is skipped as N/A when you don't use
   `git-pr`);
5. writes the `CLAUDE.md` and `GEMINI.md` pointers (Claude Code and Gemini CLI each read their own)
   and reminds you to commit and push them;
6. **offers a Claude Code allow rule** (a terminal only, asked once, never written silently) — see
   [the allow rule](#the-claude-code-allow-rule-init-run-offers) below.

Re-running is always safe: every step is re-verified live, and `.tai/init-state.json` is just a
cache it rebuilds — never copy it between clones. For a brand-new project, the one thing it
can't do is Jira admin provisioning (TAI's issue types and a `Persona` field): its to-do list
says what's missing, and the checklist below has the click-paths. Run
`npx --prefix ~/.tai-framework tsx ~/.tai-framework/src/hosts/cli.ts init status` any time to
see progress.

#### The Claude Code allow rule `init run` offers

In auto mode Claude Code judges each command one by one, and it can deny a routine TAI command partway
through a long run (one clean-up had 47 `page link` calls go through and 5 identical ones denied, and the
session stalled). So `init run` offers to add a narrow allow rule to your project's
`.claude/settings.local.json`. It shows the exact rules first and writes them only if you answer yes.

- **Covers:** TAI's `issue` and `page` commands, and the read-only `ready`, `pr-ready`, `work`, `verify` and
  `git-pr` `review-prep`, `comments` and `render-findings`, each with and without `--as <persona>`.
- **Never covers:** `git-pr merge`, `git-pr review`, `init`, or anything else, so merges and approvals still
  reach you.
- **Why that file:** the rule names this machine's TAI install path, so it belongs in the personal file
  Claude Code keeps out of git, not in a committed `settings.json`.
- **Safe to re-run:** an existing file keeps every other setting and rule, and a second run adds nothing
  twice. A file that is not valid JSON is left alone.
- **Remove it:** delete the lines that name `cli.ts` from the `"allow"` list in `.claude/settings.local.json`.

The full manual admin steps (exact Jira/Confluence click-paths, the complete `.env` var
reference, the Bitbucket and GitHub token scopes) live in
[`docs/target-project-setup-checklist.md`](docs/target-project-setup-checklist.md) and
[`.env.example`](.env.example) — read those before running `/tai-init` on a brand-new project,
since the Jira/Confluence provisioning steps need you to do things in the UI first.

**Environment variables at a glance** (see `.env.example` for the authoritative, fully
commented list):

| Variable | Used for | Required when |
|---|---|---|
| `TAI_PROJECT_KEY` | Jira project key (or a local project name) | Always |
| `TAI_BACKEND` | `filesystem` (default) or `jira` | Always (defaults to `filesystem`) |
| `TAI_ROOT` | Local cache/data folder | Optional, defaults to `.tai` |
| `TAI_HUMAN_ID`/`TAI_HUMAN_NAME`/`TAI_HUMAN_EMAIL` | Who's acting | `filesystem` backend |
| `TAI_SPACE_KEY` | Confluence space key (never assumed to equal `TAI_PROJECT_KEY`) | `jira` backend |
| `TAI_JIRA_SITE_URL`/`TAI_JIRA_EMAIL`/`TAI_JIRA_API_TOKEN` | Real Jira/Confluence auth | `jira` backend |
| `TAI_GIT_HOST` | `bitbucket` or `github`; written by `init run` from `origin` | Optional, read from `origin` when unset |
| `BITBUCKET_EMAIL`/`BITBUCKET_API_TOKEN` | Real PR create/review/merge on Bitbucket | `git-pr`/`/tai-pr` on Bitbucket |
| `GITHUB_TOKEN` | Real PR create/review/merge on GitHub | `git-pr`/`/tai-pr` on GitHub |
| `TAI_GIT_REPOS` or `TAI_GIT_WORKSPACE` | Which repo(s) `/tai-ready` checks for open PRs | `git-pr`/`/tai-pr` |
| `TAI_PR_REQUIRED_APPROVALS` | Approvals a PR needs on its current commit before it can merge | Optional, defaults to `1` |
| `TAI_PR_SELF_REVIEW` | On GitHub, lets a PR's author record a self-review that counts as one approval (GitHub refuses an author's own approval) | Optional, for a one-person GitHub project |
| `TAI_CHECK_COMMAND` | The command `git-pr check` runs on a PR's head (for example typecheck, lint and tests) | Optional |
| `TAI_STALE_BACKLOG_DAYS` | Days before an untouched Backlog ticket shows up in grooming | Optional, defaults to `60` |

## Usage

Everything below is a slash command inside Claude Code or Gemini CLI, once TAI is
installed and a project is configured (or you're using the filesystem quickstart above).

| Command | What it does |
|---|---|
| `/tai-init` | Set up (or check the status of) a target project — see [Configuration](#configuration). |
| `/tai-ready [persona]` | "What's ready for me/this persona to work on?" — the entry point when you don't have a specific ticket in mind. |
| `/tai-work <ISSUE-KEY>` | Load a ticket's briefing and invoke the persona that owns it — the entry point when you do. |
| `/tai-pr create\|review\|merge` | Open, review, or merge a real PR for a `Dev` subtask, using TAI's own structured-findings review flow. |
| `/tai-audit` | Report-only sweep of the open backlog for staleness/drift (stale notes, missing links, decision drift, …). |
| `/tai-kickoff [initiative]` | Start a project or a new initiative with Perry (PM): she checks what Epics and Kickoffs already exist, then creates the Epic + Kickoff Story. Needs no ticket, and works on a fresh project or one that already has Epics. |
| `/tai-retro [epic \| since=<date>]` | On-demand retrospective with Perry (PM): a briefing of what was cancelled, raised as Bugs, sent back, overridden or approved stale in a window (an epic's life, `since=`, or the last 30 days); she asks a few questions, writes the retro page and files action items. Needs no ticket. |
| `/tai-groom [epic]` | Backlog grooming with Perry (PM): a briefing of the whole board, or one epic — sequence Kickoffs, schedule a first wave, promote unblocked work, assign owners. Needs no ticket; every change is proposed and applied only after you confirm. |
| `/tai-change [epic] <what changed>` | Course-correct after a change in scope or direction: Perry (PM) reads the open board and its linked documents, and proposes a batch of cancels, rewords, new tickets and page revisions, applied only after you confirm. Needs no ticket. |
| `/tai-small <request>` | The light lane for a very small change (one you could describe in two sentences): creates the Story or Bug and its Dev subtask in one command, both in To Do. Review and the merge gate still apply. |
| `/tai-verify <STORY-KEY>` | Check a Story's or Bug's finished work against its numbered `AC-n` acceptance criteria: Tessa (Tester) reads the criteria and the Dev PR diffs and posts one `Verified:` / `Not verified:` comment. Show-only; nothing is blocked. |

`/tai-ready` shows live state, in one numbered list: what's **In Progress**; what's **Ready Work**;
Stories and Bugs **ready to verify** and **ready to close** (verified, with nothing open); and,
when a git host is configured, **PRs ready for your review** (including a re-review when new
commits landed after your decision), **PRs ready to merge**, and approved PRs **waiting on
something** with the merge gate's reasons. Picking a number does what that section says.

Claude Code and Gemini CLI both run every command. The one difference is that in Claude Code
the code review runs in a fresh-context subagent by default; Gemini runs the same steps in the
same session.

**A typical flow, end to end:**

```
you> /tai-ready
      → empty backlog; it tells you to run /tai-kickoff

you> /tai-kickoff <your idea>
      → Perry creates the Epic + Kickoff Story, then Ada (Analyst) does real
        discovery with you, proposes an Epic/Story breakdown, and you discuss
        and probe it together before anything downstream is created

you> /tai-ready
      → the first real Story is now unblocked and shows up here

you> /tai-work PROJ-12
      → Dario (Developer) picks up the Dev subtask, implements it, opens a PR

you> /tai-pr review
      → applies Cole (Code Reviewer)'s standard: fetches the real diff,
        produces structured findings, shows them to you, and stops — you
        decide whether to post them and whether to approve/request changes

you> /tai-pr merge
      → merges once approved and the merge gate is met, and marks the Dev subtask Done

you> /tai-verify PROJ-12
      → Tessa (Tester) checks the finished work against the Story's numbered
        acceptance criteria and posts one Verified:/Not verified: comment

you> /tai-ready
      → PROJ-12 is listed under "Ready to close": pick it, see the Verified:
        comment, and close it

(A change small enough to describe in two sentences can skip the up-front setup:
 /tai-small creates the Story and its Dev subtask in one go. Review and the merge
 gate still apply.)
```

Nothing here is autonomous — see "Nothing runs on a timer" above. Each arrow in that flow
is a real command a human ran (or explicitly asked their AI CLI to run), never a
background process.

| Persona | Name | Owns |

Every persona's exact permissions, checkpoints, and behavior are documented in
[`src/personas/*.md`](src/personas/) — those files (plus [`src/workflows/*.md`](src/workflows/))
are what your AI CLI actually reads when you invoke a persona; this table is just an
orientation map.

## Workflow types

Every Story-level ticket is one of four types, each with its own subtask set and
precedence graph (full detail in [`src/workflows/`](src/workflows/)):

| Type | Purpose |
|---|---|
| `Kickoff` | Discovery, requirements, and UX design for a new initiative, before implementation is scheduled. |
| `Story` | The standard implementation unit — design → dev → test → deploy. |
| `Bug` | A reported defect — triage → investigate → fix, skipping Kickoff-style discovery. |
| `Spike` | A time-boxed investigation into one specific question, ending in a recommendation, not shipped code. |


## Developing TAI itself

If you're working on `tai-framework`'s own source (not just using it against a target
project), see `PROJECT_BRIEF.md` and `CLAUDE.md`/`GEMINI.md` for the project's design and
working conventions.

```bash
npm test           # full test suite (node's own test runner)
npm run typecheck  # tsc --noEmit
npm run lint       # eslint
npm run build      # compiles to dist/
```

All three of test, typecheck and lint pass before a PR is opened. Live tests and throwaway
tickets go in a scratch Jira project, never a real one; see [`project-context.md`](project-context.md).

## Contributing

Internally, every change to this repo ships through TAI's own real Jira ticket → branch →
PR → structured-findings review → merge pipeline (tracked in [`CHANGELOG.md`](CHANGELOG.md)) — that's this project dogfooding itself, not something external contributors
need access to. From the outside, a normal fork → branch → PR flow works fine:

1. **Read [`PROJECT_BRIEF.md`](PROJECT_BRIEF.md) first.** It's the single source of truth
   for TAI's design, decisions, and open questions — and
   [`CHANGELOG.md`](CHANGELOG.md), its revision history, explains the reasoning behind anything that looks
   surprising (the *why*, not just the *what*).
   A change that contradicts an already-settled decision needs to either follow it or open
   the discussion to revisit it, not quietly work around it.
2. **For anything beyond a small fix, open an issue first** to discuss the approach —
   especially for anything touching [`src/personas/*.md`](src/personas/) or
   [`src/workflows/*.md`](src/workflows/), since those files are the actual behavioral
   contract an AI CLI reads at runtime, not just documentation.
3. **Fork the repo, branch, and make your change.**
4. **Before opening a PR, make sure all of these pass clean:**
   ```bash
   npm test
   npm run typecheck
   npm run lint
   ```
5. **Open a PR against `main`** with a clear description of what changed and why,
   referencing the issue it addresses if there is one.
